# agent-guards

A Hermes Agent plugin that blocks recurring agent mistakes before a tool runs and keeps delegated Kanban work moving. Every check fails open: an internal error never blocks a tool call.

## What it does

Terminal blocks:
- foreground `sleep` of 30 s or more, or a `for`/`while`/`until` loop holding a `sleep` of 15 s or more (run the wait in the background with a notification, or poll once and re-issue without sleeping; heredoc bodies and quoted strings are exempt);
- `gh pr merge` without `--match-head-commit`;
- `osascript`;
- `git push --force`/`-f` without `--force-with-lease`;
- in a worker process, `github_contact`: commands that contact people on GitHub — review requests (`gh pr edit --add-reviewer`, `gh pr create --reviewer`, `gh api` POST to `.../requested_reviewers`, every `gh pr review`), issue assignees and comments whose body `@mentions` a user or org/team (inline or via a readable body file). Mention-free comments stay allowed; `@me`/`@copilot` and removal flags are exempt; on assignee flags the authenticated login is also exempt (self-assignment contacts nobody — resolved once via `gh api user` and cached; unresolvable login fails closed). Message: contacting people needs the owner's approval — when the setup documents a merge command (env `AGENT_GUARDS_MERGE_HINT`), the message names it for a CODEOWNERS-only gap on a green exact head; otherwise, and if the card forbids merging or the diff needs independent review, `kanban_block` with `kind=needs_input` — do not just wait.

Attachment block:
- `kanban_attach` with more than 256 characters of inline base64. Models transcribe those bytes and corrupt them; attach by path (`artifacts=[absolute path]` at handoff, or `hermes kanban attach <task_id> <path>`).

Argument normalization (the call proceeds with corrected arguments):
- empty optional Kanban arguments become absent;
- `skill_view` names of the form `x:x` become `x`;
- a Kanban `task_id` sent as the literal `$HERMES_KANBAN_TASK` becomes absent, so the worker's own task is used.

Other guards:
- `paas_promote_gate`: in every process, blocks a terminal command that dispatches the `paas-promote` workflow (`gh workflow run paas-promote`/`paas-promote.yml`) when the target environments (`-f/--field SUPRAENVS=...`, defaulting to `des` when the field is absent) include `des` while the `-f/--field LABELS=...` value does not carry the `auto-approval` label — the shape that leaves the generated deployment pull request open because only that label makes the bot merge it. The block message names the missing label and the exact corrected flag. Values are read from `-f KEY=VALUE`, `--field KEY=VALUE` and quoted forms plus leading `KEY=VALUE` assignments; PRE-only or PRO-only dispatches, other workflows, other gh commands, mentions inside echo/quoted strings, and any unanalyzable shape (shell expansion, unbalanced quotes, env-wrapped dispatches) pass — it catches slips, not deliberate evasion, and fails open.
- `repeat_guard`: blocks an identical call that already failed twice in the session with nothing changed since.
- `checkpoint_gate`: in a worker process, once the run passes 400 API calls (read from the `api_request_id` tail) without a successful Kanban checkpoint comment (or review/complete/block), non-checkpoint tool calls are blocked until one is written; the duty re-arms every 25 calls, so a long run keeps leaving board-visible progress instead of dying at the iteration cap holding everything in hand.
- `skill_size`: blocks any write that grows a skill markdown file past its limit (`SKILL.md` 6000 characters, other `.md` files 12000). Shrinking is always allowed, so oversized skills can be split into an index plus a reference tree.

Worker setups (only when `kanban.default_assignee` is set in the profile config):
- `kanban_policy`: `kanban_create` must use that assignee, must not use triage, must not override execution settings and must carry an `Acceptance` heading followed by a numbered list of checkable criteria; `kanban_request_review` may only name that worker as reviewer.
- `inventory_rule` (lead-only, pre_llm_call): at the start of every lead user turn it injects one short instruction — before delegating anything, write the inventory of the request's independent atomic units, then create one Kanban card per unit, either in this turn or at the moment the plan covering that unit is approved (whichever the workflow prescribes), exactly one unit per card, as many as the work genuinely allows (child cards with `parents` are exempt). Each acceptance item on a card states the input range it must survive and the final verification surface, and any premise the plan depends on is named with the cheap check that would falsify it; a running card is never widened — new work found mid-run becomes a new card with a dependency edge on the running one. The rule arrives as injected context at the turn prologue, so the lead plans the split before the first card is created and nothing is ever blocked. It registers nothing but the hook (no `pre_tool_call` entry), fires once per user turn (the host only invokes `pre_llm_call` at the turn prologue; tool-result iterations replay the same message), returns only `{"context": ...}` — a worker-context call (`HERMES_KANBAN_TASK` set) returns `None` so workers never see it — and is bounded by an LRU of 200 turns so a long session cannot grow it without limit.
- `lead_delegation`: in the lead process (no `HERMES_KANBAN_TASK`), blocks `write_file`/`patch` under repository roots (`~/git_repos`, override with `AGENT_GUARDS_REPO_ROOTS`) and `git commit`, `git push` and `gh pr create` aimed at them. The lead investigates, writes issues and cards, reviews and integrates; implementation and delivery go to a worker card.
- `completion_gate`: in a worker process, blocks `kanban_complete` on a card whose body has a numbered `Acceptance` list until `metadata.acceptance` maps every item number to its evidence. An item that cannot be met calls for `kanban_block`, not completion. Evidence that itself admits an item is unmet ("not yet", "not met", "pending merge/review/deploy", "remains open") also blocks. Reviewer completions (run claimed from review, or `metadata.review_verdict`) are blocked too when unevidenced Acceptance items name post-review steps (merge, deploy, close): the approval must record its verdict and hand the card back to the implementer through `kanban_request_changes` (completion from review closes the whole card, and there is no approved-and-returned state). Reviews whose remaining items do not name post-review steps complete as before.
- `review_gate`: `kanban_request_review` is blocked until the session's latest `todo_list` holds one closed item per pre-review check (Contract coverage, Failure lifecycle, Model evidence, Claims within evidence, Real boundary, Stale siblings, Self reproduction, Claims anchored): completed with a receipt anchor in the item text (a receipt path, artifact file, file:line reference, hash, exit code or test count), or cancelled with `N/A: <reason>`.
- `stop_gate`: after a blocked lifecycle call (review gate, policy, any tool error), a final text-only reply like "Building the todo list, then requesting review:" is answered with a `pre_verify` continue directive telling the worker to actually call `kanban_complete`/`kanban_request_review`/`kanban_block`; the nudge also names the rejected tool and the first 120 characters of its error so the worker fixes the named cause. Without it the core stop-guard counts the blocked call as done and the run exits rc=0 as a protocol violation. `pre_verify` only fires in turns that edited files (`write_file`/`patch`), so pure-read runs get no nudge from this gate alone.
- Retry instruction: every guard block of a lifecycle call (`kanban_policy`, `completion_gate`, `review_gate`, `handoff_gate`, `schedule_gate`, and `repeat_guard` when the repeated call is a lifecycle call) ends with the same demand — retry the lifecycle call in this same response; a text-only reply ends the run as a protocol violation. This is the one lever a block message controls, and it covers read-only runs that `stop_gate` cannot reach.
- `handoff_gate`: the first `kanban_block` of a session whose reason says the worker's part is finished and only lead-owned steps remain (merge, deployment, publication, approval) is bounced with advice to hand off through `kanban_complete` or `kanban_request_review`; repeating the call lets a genuine decision block through.
- `backup_copy_gate`: in a worker process, blocks `kanban_complete`/`kanban_request_review` whose summary, result or metadata declares a kept/preserved backup, rollback, pristine or before-copy of prior state ("backup kept", "rollback copy preserved", "defective versions backed up"). Rollback is git: the worker deletes the copy and recovers prior state from git history instead. Statements that no copy was kept, or rollback done via git, pass.
- `schedule_gate`: in a worker process, blocks `kanban_schedule`. Scheduling ends the run and sets no timer, so a self-scheduled card stops until someone notices. Workers wait for CI, deployments or executions with background processes and notifications; a real external dependency is a `kanban_block` with its release condition.
- `published_head_gate`: in a worker process, blocks `kanban_request_review` when it names a GitHub PR and a commit (`metadata.commit` or `metadata.head`) that is not the PR's live head, so a reviewer never freezes an unpushed candidate. Fails open if either value is missing or GitHub cannot be read.
- `pr_acceptance_gate`: in a worker process, keeps the published-PR completion duty visible and the rejection loop bounded. When the card's persisted `completion_contract` names a GitHub publication, a `kanban_show` of the worker's own card gains one reminder stating that `kanban_complete` must carry `metadata.published_pr` (and what value satisfies it); a `kanban_complete` rejected as "PR acceptance missing" gains the exact fix on the rejection text; and after two counted rejections, a retry whose `published_pr` still does not match the contract is blocked with the contract restated, the publication-binding hazard named (under an OWNER/REPO contract the first matching `published_pr` is rewritten into the contract permanently), and the `kanban_block(kind="needs_input")` escape required in the same response. A successful completion clears the count, so a later card in the same session starts clean.
- `approval_wait_gate`: in a worker process, blocks the silent hours-long wait on an approval-only pull request (a PR green on every automated check with the CODEOWNERS approval as the only open gate, polled with background loops for hours). When the exact head of a polled PR is green and review approval is the only open gate, readiness polls of that PR (`gh pr checks`, `gh pr view --json statusCheckRollup|mergeStateStatus|…`, `gh api …/pulls/<n>`, poller helper scripts such as `pr_status`/`pr_wait_checks`) return the verdict line and the authorized moves instead of running: merge the verified head with the setup's documented merge command if one exists (env `AGENT_GUARDS_MERGE_HINT`), and `kanban_block(kind="needs_input")` so the lead is notified otherwise. A repeating `kanban_heartbeat` note that admits the approval-only wait is blocked from the second one on (the first passes so the situation can be time-stamped). Pending or failing checks, drafts, conflicts and mergeable-read errors are not verdict names, so their polls flow through untouched, and the verdict is cached for 15 minutes so repeated polls cost at most one GraphQL round-trip per quarter hour.


Stale card wake (`stale_wake`): it wakes each chat subscribed to a triage/todo/ready/review/blocked/scheduled card whose last state change is at least 5 min old, once per card state. A todo card with an unfinished parent is skipped: it waits on a dependency and the dispatcher starts it when the parents finish. It needs gateway injection to be allowed:

Review loop wake (`review_loop`): it wakes each chat subscribed to an open card that has reached 3, 6, 9... review rounds with changes requested, once per threshold, with the latest requested change and a four-item decision menu the lead picks from: narrow the contract and send the card back (when the recent findings are sentence or number integrity only, the message carries the convergence contract that worked before — every numeric sentence names the script and output that print it, or is removed; the reviewer re-executes the scripts, checks that mapping and the named lines, and opens no new analyses), continue over the real defects (checking whether they are new or repeats and whether a successor card is needed), split the card, or take it over. Rather than one vague "decide here" nudge, the menu names the real escape routes so the lead cannot answer without committing to one, and the loop breaks at that turn instead of after another silent threshold. The old wake was 424 rendered characters at 9 rounds; this one is 1004, still one short injected message. It uses the same gateway injection setting.

Churn warning (`churn_wake`): it warns each chat subscribed to a non-archived, non-done card whose worker runs have reached 10, 20, 40… or whose change-requests have reached 5, 10, 20…, once per threshold, with the last change-request reasons, so the lead decides to split the card, narrow the acceptance or confirm continue. It is a warning only: nothing is blocked. It uses the same gateway injection setting.

The three wakes sweep on every dispatcher tick but only when the board has changed since the last sweep (`board_watch`): each hook tracks the id of the newest wake-relevant `task_events` row — state events for the stale wake, `changes_requested`/status/timing events for the other two — and skips a tick whose event log is at the recorded cursor. Any successful Kanban mutation from any process (worker or lead) also pokes a shared marker file that forces the next tick's sweep, so a wake lands within one tick of the event that caused it instead of waiting out the previous per-hook ceilings of 1 h / 5 min. Stale is time-based, so the stale wake additionally stores the moment the next un-woken card crosses its 5 min age in its cursor and sweeps on the first tick at or past that moment even on a fully quiet board (nothing else sweeps on time alone). Watermark and dedup semantics are unchanged: a wake still fires once per card state or threshold and re-arms exactly as before.

Waiting-on-external-gate wake (`waiting_wake`): on every dispatcher tick (unthrottled, its own hook) it watches each running card's `heartbeat` notes since the run boundary (the newest `spawned`/`claimed` event) for an admission of waiting on something outside the worker's control — a merge bot or auto-merge, a CODEOWNERS/review approval, a deploy, rollout, promotion, release or CI run. It keys on the run's wait streak: the consecutive wait-admitting notes counted back from the newest non-empty heartbeat (empty heartbeats neither start nor break the streak, a normal progress note ends it). When the newest non-empty note admits a wait and the first note of that streak is 15 minutes old (the worker is still waiting, not past it) every chat subscribed to the card is woken once, quoting the latest note and how long the streak has run, so the card's owner decides: intervene (merge, approve, re-run the pipeline), take the card over, or tell the worker to `kanban_block(kind="needs_input")`. Heartbeat notes reach nobody, a waiting worker cannot unblock itself, and a running card is never stale-checked, so without this wake the wait is silent. The external actor must follow the wait phrase (rate cooldowns and local-tooling waits never count) and a note that merely discusses waits can slip through: the bound is one short injected turn per run, quoting the note for the owner to judge. It uses the same gateway injection setting.

Dispatcher-stall wake (`stale_wake.stall_wake_on_tick`): on every dispatcher tick (unthrottled, so it runs alongside the 5 min stale wake) it wakes each chat subscribed to a todo/ready card whose last 30 task events are all `respawn_guarded` events with `reason=active_pr` — the dispatcher's 24 h PR-URL respawn guard is holding the card out of the ready queue every tick (a full GitHub PR URL in a comment reads as "a worker already opened a PR"). It wakes once per guard episode — the trailing run of guard events; the wake is not re-armed while the run only grows, and re-arms when the card leaves the stalled set and enters it again — with the release levers: reword the comment (cite the PR as `owner/repo#N` — the guard only matches full URLs), assign the card explicitly, or archive it if the outcome was delivered elsewhere. It uses the same gateway injection setting.

- `unreconciled notice` (`notification_reconcile`): on the first tick after board activity it checks each out-of-running card whose latest notifiable state event (the kinds the gateway renders a text ping for — completed, blocked, gave_up, crashed, timed_out, status, review_requested, changes_requested, block_loop_detected) was never confirmed delivered: no subscription's `last_ping_event_id` checkpoint covers it, including the no-subscription case. A state inside a 60 s grace window, or one whose subscription still exists, is only recorded (`pending`) — the gateway's own notifier is at-least-once and either delivers it or drops the subscription after repeated failures. When the recorded state's delivery path is gone (subscription deleted while the checkpoint still lags) the hook sends one terse notice per state through the same gateway injection, naming the event kind and its recorded cause, to the remembered subscriber origins; later uncovered transitions of the card notify once each too, keyed on the event id in `~/.hermes/state/kanban-notify-reconcile.json`. First sight of an uncovered card without any record is adopted silently (its delivery history is unknowable once the subscription row is gone), an unchanged state never re-notifies, a failed injection retries on the next sweep, and delivered/closed states drop out of the record. It never touches worker processes or the board database, and never restarts anything.

Lead chat scoping (`workspace_scope_gate`, transform hook): in a lead process (no `HERMES_KANBAN_TASK`, `kanban.default_assignee` configured) with a messaging-origin session, a `kanban_list` result is rebuilt from the board so it contains only the cards the calling chat thread subscribes to (`kanban_notify_subs` platform/chat_id/thread_id): the transform re-queries the board under the call's own `assignee`/`status`/`tenant`/`include_archived` filters, keeps the subscribed set, applies the call's `limit` to that owned set, and recomputes `count`/`truncated`/`next_limit` with the handler's own summary shape; `hidden_foreign` reports filter-matching cards on the board that belong to other chats. A window that already shows exactly the owned view passes through byte-identical; `kanban_show` of a foreign card stays allowed; worker processes, CLI, cron and TUI (no origin) pass through untouched; any read/parse/rebuild failure fails open (result unchanged).

Lead PR-URL comment gate (`pr_comment_gate`): in the lead process only, blocks a `kanban_comment` whose body carries a full GitHub PR URL onto a todo/ready/blocked card — the same respawn-guard stall the stall wake reports on, stopped at the source. The block message names the `owner/repo#N` citation to use instead. Worker comments are untouched (the worker's own PR URL is the guard's legitimate input), and full URLs stay fine on running/done cards.

```yaml
plugins:
  entries:
    agent-guards:
      allow_gateway_injection: true
```

## Install

```bash
hermes plugins install shard-guard/hermes-agent-guards --enable
```

## Tests

```bash
python3 -m pytest -q tests
```

Updates: installs without `--ref` follow `main`; with `plugins.auto_apply: true` Hermes pulls new commits on its update-check cadence (`plugins.auto_update_check_hours`). A private fork needs read access for the Hermes host, for example a read-only deploy key.
